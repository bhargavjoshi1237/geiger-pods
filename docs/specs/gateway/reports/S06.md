## Deviations from the spec or AWS, with reasons

1. No FKs to `pods.rest_methods`/`pods.integrations` (S03/S04 land in parallel; S03 uses
   `pods.rest_methods` as the spec predicted). Plain uuid columns + compile-time checks;
   FKs can be added once those tables exist. `project_id` is denormalized for RLS.
2. `validateProcessing` warns (not errors) on unknown `$` mapping sources and on a missing
   default integration response — AWS fails some of these at deploy; warnings keep
   forward-compat imports (S13) deployable while still flagging them.
3. VTL leniency: method calls on null return null (render empty); undefined variables are
   falsy in `#if`/`#foreach`/`#set` but render literally (`$x`) or empty (`$!x`) in output.
   Unknown methods, bad `$util.parseJson`, and pollution writes throw (→500). This mirrors
   Velocity's lenient core while keeping real errors loud.
4. `br` response compression is implemented but off unless `brotliEnabled` (spec: Pods
   extension, off by default). Subdomain CORS wildcards likewise behind
   `features.corsWildcardSubdomains`.
5. `CONVERT_TO_BINARY` request handling only base64-decodes when the text round-trips as
   base64, else keeps the bytes — avoids corrupting plain-text bodies AWS would reject.
6. Falsy follows Velocity for `""`, `[]`, `{}`, `0`, `false`, null (documents the choice;
   AWS inherits Velocity semantics here).
7. `renderCustomGatewayResponse` is async (dynamic imports avoid a gateway-responses ↔
   processing import cycle at module load).
8. `listResponseTypes` default for `DEFAULT_4XX` is 400 (S01 renders it as 400/500 already).
